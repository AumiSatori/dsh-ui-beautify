## 多行草稿回车：补间与收缩共用一条时间线（2026-10-28）

本机 `localhost:8442` 实测（1400×900，轻量玻璃 + 对话延伸到输入栏后方，6 行草稿回车；探针取可见正文一行，在晚于插件的 ResizeObserver 回调里读取，即实际绘制帧）发现两处残留：

- 宿主跟随控制器在自己的 ResizeObserver 里写 `scrollTop`。补偿用的尺寸观察器在插件启动时创建，回调排在宿主之前，这次写入要等下一帧 scroll 事件才被补偿，正文先闪到新位置 112px 再弹回。
- 输入框收缩（220ms）每帧拉回一点原生滚动，补偿每帧都把 280ms 缓动从头重启，目标始终按"高输入框"计算，正文先停住、再滞后追赶。

现在每次发送新建尺寸观察器（回调排在宿主之后，同一帧补偿）；收缩期间从本插件 `dcb-composer-submit` 动画读出剩余收缩量，并入缓动终点，收缩造成的负向位移只平移起止值、不重启时间线，正文一次缓动到真实落点。行增删重建补偿时也沿用同一时间线。无收缩动画时（关闭消息动效）行为与原来相同。

实测（同一会话、同一节奏）：修复前首帧闪动 112px、反向 2 次、收缩期间停顿约 240ms；修复后两次发送均为反向 0、无闪动、单帧最大位移约 21–26px（宿主丢帧处），草稿清空、焦点保留、补偿标记与样式全部释放。

## v0.5.0 回归：流式跟随下多行草稿回车停顿（2026-11-01）

v0.5.0 把发送补偿改成流式弹簧（`stream-spring.js`），默认开启的「流式逐字渐显」让每次发送都走这条路径。输入框收缩的每一帧都会进入"沿用时间线"分支，但新弹簧从 `job.from`（时间线起点的偏移）以 `currentTime=0` 重新起步，正文因此被钉在回车时的位置，直到收缩结束才开始移动。

现在收缩帧重定向正在运行的弹簧时，从它当前的绘制位置加上本帧原生位移起步，并沿用当前速度；终点仍是剩余收缩量，正文一次连续滑到落点。

本机 `localhost:8442` 实测（1400×900，轻量玻璃 + 对话延伸到输入栏后方，6 行草稿，探针在晚于插件的 ResizeObserver 回调中读取绘制帧）：修复前开始移动前约 300ms 不动（576px 保持），随后补一步 26px；修复后 54ms 开始移动，收缩期间静止帧 0、反向 0。合成回归新增 `stream-single` / `stream-multiline`：修复前反向 4–5 次、收缩期静止帧 13–17；修复后反向 0、静止帧 ≤1。

单行发送约 115ms 处偶见一次 ~33px 的台阶，修复前后都有；同帧的长动画帧来自宿主 `dsh-api-gateway` 的 WebSocket 处理（74ms，含 25ms 强制布局），插件补偿的起止值连续，不属于本插件。

## 桌面端：发送收起改为合成器动画（2026-11-01）

桌面端调试（本机临时调试端口，测完已按原参数重启）发现：宿主在输入区每次改变尺寸时都会把高度写进对话区上可继承的 `--dsh-composer-height`，整页（约 2,000–7,800 个元素）随之重算样式，每次约 30ms。原来的收起动画逐帧改输入区高度，于是每一帧都触发这次重算。

- 收起改为：真实布局一次到位，在输入卡片后面放一个固定的裁剪框，里面是完整高度的卡片外观副本，只用 `transform: translateY` 下滑到新的上沿。只有位移在动，由合成器绘制，清空长草稿造成 100ms 以上的主线程阻塞时也照常运行；卡片自身的材质在动画期间临时隐藏，结束后恢复，过渡属性延后两帧恢复，避免强制整页重算。
- 发送补偿的 MutationObserver 只在对话行增删时才读取 `scrollTop`，不再在每次 React 提交中强制排版；会话切换仍立即取消。
- 行被替换时从相邻行的当前偏移接续；行候选集合变化时，仍在滑动的行保留在动画里，不再整屏回跳。

剩余的长帧主要来自宿主自身渲染新一轮对话（100–160ms，React 提交、样式与布局）。CSS 选择器统计中没有单条突出的高开销选择器。
