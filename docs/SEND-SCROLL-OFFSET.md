# 发送补偿的行数上限与放弃方式

范围：`src/composer-scroll-motion.js`。只处理发送后原生跟随时绘制的滚动补偿，不改宿主的滚动位置、事件、锚点和跟随控制器。

## 这次修的抖动

密集长会话里一屏能排到 20 行以上。`candidates()` 收集补偿行时上限是 16 行，超过就 `return null`，`flush()` 接着 `release()` —— **整批补偿在下一帧被取消**，已经隐藏的原生跳变当场露出来。真实页面（1440×960、61 行会话、每 80ms 追加 45px 模拟流式增长）实测：单帧可见位移 **88.48px**，三次 `candidates-null` 释放。

同一段代码还有两处会放大问题：

- 释放是「立刻 cancel」，补偿量在 0 帧内归零，视觉上就是硬跳；
- 方向反转判定用的 `layoutChanged` 在每次 `sample()` 后被清掉，输入框收缩之后的负向 clamp 会被当成用户中断，再触发一次硬跳。

## 现在的做法

- 行数上限从 16 提到 48，并且**上限只截断收集，不再中止整次补偿**（`break` 而不是 `return null`）；面积预算和超大行仍按原样放弃，因为那两种情况下逐行补偿会在同屏内容之间撕开。
- 我们在动的行不再被当成「已有 transform」跳过，否则第二次补偿会把整屏行全部滤掉。
- 放弃补偿不再瞬断，改为 160ms 淡出回布局位置；用户主动中断（滚轮、指针、阅读键、隐藏窗口、卸载、切会话）仍然立即释放，不吃输入。
- 方向反转只在该次发送**没有任何收缩**、且距上一次布局收缩超过 240ms 时才交还宿主。

## 验证

`test/composer-scroll-motion-browser.mjs` 7 项通过，新增「密集正文越过行数上限仍继续补偿」一项：断言标记行数 > 16、各行补偿量一致、可见正文仍在补偿、flow 仍为 clip。

真实页面（`localhost:8442`，注入本次构建逐帧采样，未提交任何消息、未改动会话数据）：同一节奏下单帧最大可见位移 88.48px → 6.23px，方向反转 3 次释放 → 0 次，补偿行数 16（触发放弃）→ 19。

## 边界

页面里若不是助手流式增长、而是宿主自己做 smooth 滚动，补偿和原生缓动会叠在一起；本次没有改这条路径，遇到时仍按原来的方向反转规则交还宿主。
